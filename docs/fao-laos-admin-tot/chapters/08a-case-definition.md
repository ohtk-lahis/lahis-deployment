# 7.2 Case Definition: ออกแบบและกำกับกติกาเปิด Case อัตโนมัติ

`Case Definition` คือกติกาที่บอกระบบว่า Report แบบใดควรกลายเป็น `Case` โดยอัตโนมัติหลังระบบรับรายงานใหม่ บทนี้สอนให้ System Admin และผู้ฝึกสอน **อ่าน ออกแบบ ตรวจทาน และทดสอบกติกา** อย่างเป็นขั้นตอน ไม่ใช่สอน Officer เขียนเงื่อนไขใน Dashboard

1. ผู้รับผิดชอบกำหนดนโยบายการเฝ้าระวัง
2. System Admin ตรวจทาน `Rule design sheet`
3. System Admin กำหนด `Case Definition`
4. Report ใหม่ตรงเงื่อนไข
5. ระบบเปิด Case และ Officer รับงานเพื่อติดตาม

กติกาที่กว้างเกินไปอาจเปิด Case มากเกินจำเป็น ส่วนกติกาที่แคบหรือเขียนผิดอาจพลาดเหตุที่ควรติดตาม จึงต้องแยกการตัดสินใจเชิงนโยบายออกจากการพิมพ์เงื่อนไขในระบบให้ชัดเจน

## 7.2.1 แยกหน้าที่ก่อนเริ่มสอน

| บทบาท | หน้าที่ในเรื่อง Case Definition |
|---|---|
| เจ้าของนโยบาย / ผู้เชี่ยวชาญโรค | กำหนดว่าเหตุใดควรเปิด Case และยอมรับเกณฑ์ใด |
| System Admin | แปลงกติกาที่อนุมัติแล้วเป็น Case Definition, ตรวจทาน และจัดการทดสอบ |
| Officer | รับ Case ที่ระบบเปิด หรือใช้ `Promote to case` เมื่อจำเป็น; แก้ Case Definition ไม่ได้ |
| Reporter | ส่ง Report ผ่าน Mobile; ไม่เห็นและไม่ตั้งค่า Case Definition |

Officer จึงใช้ [บทที่ 8](09-daily-work.md) สำหรับ `Promote to case`, การติดตาม และการปิด Case เท่านั้น

## 7.2.2 เริ่มจากกติกาที่ใช้อยู่ ไม่เริ่มจากช่อง Condition

Production ที่ตรวจผ่าน Dashboard วันที่ 8 กันยายน 2026 มี `Case Definitions` 10 รายการ: 1 รายการสำหรับ Report คนถูกสัตว์กัด และ 9 รายการสำหรับ Report สัตว์ป่วย/ตาย

ให้ใช้ตารางนี้เป็น “แผนที่นโยบาย” ในการสอนก่อนเปิดหน้าจอรายละเอียด

| กลุ่มกติกาใน Production | ความหมายที่ผู้เรียนควรเข้าใจ |
|---|---|
| คนถูกสัตว์กัด | กติกาใช้ `True` จึงเปิด Case สำหรับ Report ประเภทนี้ทุกรายการ; ผู้รับผิดชอบนโยบายควรยืนยันว่าต้องการเช่นนี้อยู่เสมอ |
| สัตว์ป่วย/ตาย: ระบุโรค | เมื่อรายงานระบุโรคที่เลือกไว้ ระบบเปิด Case |
| สัตว์ป่วย/ตาย: เกณฑ์จำนวน | แยกเกณฑ์ตามกลุ่มสัตว์ เช่น สัตว์เคี้ยวเอื้อง/สุกร และสัตว์ปีก โดยใช้จำนวนตาย จำนวนป่วย สัดส่วนต่อจำนวนทั้งหมด หรือจำนวนคอกใกล้เคียง |
| สุนัขและแมว: อาการเข้าข่ายพิษสุนัขบ้า | ใช้ชุดอาการและ/หรือโรคที่ระบุ เพื่อคัดเลือกเหตุที่ควรติดตาม |
| สัตว์กีบ: อาการเข้าข่ายปากและเท้าเปื่อย | ใช้อาการสำคัญร่วมกับการตายกะทันหัน |

ตารางนี้สรุปเจตนาของกติกา ไม่ใช่คำแปลแทน `Condition` ทุกตัว ผู้ฝึกสอนควรเปิด rule จริงเพียง 2–3 ตัวอย่างที่ต่างกัน เช่น `True`, เกณฑ์ตัวเลข และชุดอาการ เพื่อให้เห็นว่ากติกาที่อ่านง่ายอาจมีเงื่อนไขทางเทคนิคซับซ้อนอยู่เบื้องหลัง

## 7.2.3 ดูหน้าจออย่างปลอดภัย

จาก `Settings` เลือก `Case Definitions` หน้ารายการแสดง `Report Type` และ `Description` ของแต่ละ rule ก่อนเปิด `View` ให้ผู้เรียนอ่านสามส่วนตามลำดับนี้

1. `Report Type` — rule ใช้กับ Report ชนิดใด
2. `Description` — เจ้าของนโยบายต้องการให้เปิด Case ในสถานการณ์ใด
3. `Condition` — ระบบตรวจข้อมูล Report ด้วยตรรกะใด

ระหว่างอบรมให้ใช้ Production เป็นตัวอย่างแบบอ่านอย่างเดียว ห้ามกด `Add`, `Import`, `Edit` หรือ `Delete` ใน Production หน้าจอ Staging ที่ตรวจในวันเดียวกันมี `0 records` จึงไม่ควรสร้าง rule ขึ้นมาเพียงเพื่อทำภาพประกอบหรือให้ผู้เรียนทดลองกด

## 7.2.4 อธิบาย Condition เท่าที่จำเป็น

`Condition` เป็นนิพจน์ที่ระบบประเมินเป็นจริงหรือเท็จ ไม่ใช่ข้อความที่ Officer หรือผู้รายงานต้องอ่านเอง กติกาใน Production ใช้รูปแบบต่างกัน เช่น

| รูปแบบ | ตัวอย่างเชิงความหมาย |
|---|---|
| `True` | Report ทุกฉบับของ Report Type นี้เปิด Case |
| จำนวนหรือร้อยละ | จำนวนตายมากกว่าเกณฑ์ หรือจำนวนป่วยมากกว่าสัดส่วนที่กำหนด |
| ค่าเลือกหนึ่งค่า | ชนิดสัตว์หรือโรคตรงกับค่าที่กำหนด |
| ตัวเลือกหลายค่า | มีอาการสำคัญหลายข้ออยู่ร่วมกัน |
| เงื่อนไขผสม | ชนิดสัตว์ **และ** อาการ/จำนวน ต้องตรงพร้อมกัน |

ในการอบรมทั่วไป ไม่ต้องสอนให้ผู้เข้าร่วมเขียน syntax จากศูนย์ ให้สอนว่าชื่อ field, ค่า choice, วงเล็บ และคำเชื่อม `and` / `or` เปลี่ยนผลของกติกาได้ หากจำเป็นต้องแก้ rule ให้ System Admin ทำจาก Rule design sheet ที่ผ่านการตรวจทานแล้ว และมีผู้รับผิดชอบด้านเทคนิคช่วยตรวจนิพจน์

### จุดตรวจจาก Production

Rule สุนัข/แมวบางตัวใช้ field ของสุนัขเป็นเงื่อนไขตั้งต้น แล้วจึงอ้างถึงข้อมูลแมวด้วย ก่อนปรับกติกากลุ่มนี้ ควรทดสอบ Report ของแมวเพียงอย่างเดียวให้ชัดว่าเปิด Case ตามที่นโยบายต้องการหรือไม่

## 7.2.5 Rule design sheet ก่อนเปลี่ยนกติกา

ให้ผู้เรียนฝึกกรอกเอกสารสั้นนี้จากสถานการณ์สมมติ แทนการแก้ข้อมูลบน Dashboard

| หัวข้อ | สิ่งที่ต้องระบุ |
|---|---|
| ชื่อกติกาและเจ้าของนโยบาย | ชื่อที่อ่านแล้วรู้เหตุผล และผู้อนุมัติ |
| Report Type | ชนิด Report เดียวที่อยู่ในขอบเขต |
| เหตุที่ต้องเปิด Case | เกณฑ์เชิงปฏิบัติงาน ไม่ใช่โค้ด |
| ข้อมูลที่ใช้ตัดสิน | field และค่าจริงที่ตรวจจาก Form builder |
| ผลที่ควรเกิด | ใครรับผิดชอบ Case และต้องทำอะไรต่อ |
| ตัวอย่าง “เข้าเกณฑ์” | รายงานตัวอย่างหนึ่งรายการที่ควรเปิด Case |
| ตัวอย่าง “ไม่เข้าเกณฑ์” | รายงานใกล้เคียงหนึ่งรายการที่ไม่ควรเปิด Case |
| ขอบเขตและผู้อนุมัติ | พื้นที่/เวลาใช้ และชื่อผู้อนุมัติ |

System Admin จึงนำ Rule design sheet ที่อนุมัติแล้วไปจับคู่กับ `Report Type`, `Description` และ `Condition` บนหน้าจอ ไม่ควรรับคำสั่งลักษณะ “ถ้าอาการหนักก็เปิด Case” แล้วพยายามตีความเป็น rule ทันที

## 7.2.6 แผนทดสอบก่อนนำกติกาไปใช้

การทดสอบต้องแสดงทั้งกรณีที่ควรเปิดและไม่ควรเปิด Case

| กรณีทดสอบ | สิ่งที่ต้องยืนยัน |
|---|---|
| เข้าเกณฑ์ | Report ใหม่แสดงป้าย `case` และเปิดไปยัง Case ที่เชื่อมกับ Report เดิมได้ |
| ไม่เข้าเกณฑ์ | Report ใหม่ยังไม่เป็น Case |
| ค่าที่ขอบเกณฑ์ | ตรวจค่าเท่ากับเกณฑ์และค่ามากกว่าเกณฑ์ เพราะ rule จำนวนใน Production หลายตัวใช้ “มากกว่า” ไม่ใช่ “มากกว่าหรือเท่ากับ” |
| ชนิดสัตว์ใกล้เคียง | ยืนยันว่ากติกาของสุกร สัตว์เคี้ยวเอื้อง และสัตว์ปีกไม่เปิดข้ามกลุ่ม |
| อาการร่วม | ทดสอบทั้งมีอาการบางข้อและมีชุดอาการครบตามนโยบาย |

ควรทดสอบในสภาพแวดล้อมควบคุมและใช้ Report ใหม่ที่ไม่ถูกทำเครื่องหมายเป็น Test report เพราะ Test report จะไม่เข้าสู่การประเมิน Case Definition อัตโนมัติ หลีกเลี่ยงบัญชีผู้รายงานที่เพิ่งลงทะเบียนใหม่สำหรับการทดสอบนี้ และบันทึก Report ID, Case ID, เวลา และผลของทุกกรณี

![Report ที่เชื่อมกับ Case](../../fao-laos-researcher-guide/screenshots/29-dashboard-report-promote-to-case.jpg)

*ภาพที่ 7.2.1 — Report แสดงป้าย `case` และเปิดไปยัง Case ที่อ้างถึง Report เดิมได้ ภาพนี้ยืนยันความเชื่อมโยง แต่ไม่ระบุว่า Case เริ่มจากกติกาอัตโนมัติหรือจาก Officer*
